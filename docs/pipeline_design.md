# Проектирование ETL-пайплайнов (Pipeline Design)

## 1. Общая концепция

Для загрузки и обновления данных в проекте Game Deal Intelligence используются два ETL-пайплайна, оркестрируемых Apache Airflow:

- **Initial Load** — первоначальная загрузка данных из CheapShark API.
- **Incremental Sync** — периодическая синхронизация изменений.

Оба пайплайна используют Python для взаимодействия с API, PostgreSQL для хранения данных и SQL для выполнения трансформаций.

Основная задача такого разделения — отделить первоначальное наполнение базы данных от регулярного обновления информации.

## 2. Initial Load

### 2.1. Назначение

Initial Load предназначен для первоначального наполнения базы данных информацией об играх, магазинах и доступных предложениях.

Пайплайн получает данные из CheapShark API, сохраняет исходные ответы в RAW и загружает обработанные данные в CORE.

### 2.2. Логика выполнения

Общий порядок выполнения:

1. Создание записи о запуске в `raw.pipeline_runs`.
2. Получение списка игровых магазинов.
3. Сохранение исходного ответа API в `raw.raw_api_responses`.
4. Получение списка доступных предложений.
5. Сохранение исходных ответов API в RAW.
6. Загрузка и обновление справочника игр.
7. Загрузка актуальных предложений.
8. Завершение запуска и обновление его статуса.

### 2.3. Результат

После успешного выполнения:

- В `raw` сохранены исходные ответы API.
- В `core.games` загружена информация об играх.
- В `core.stores` загружена информация о магазинах.
- В `core.deals_current` находятся актуальные предложения на момент загрузки.
- В `raw.pipeline_runs` сохранена информация о выполнении пайплайна.

## 3. Incremental Sync

### 3.1. Назначение

Incremental Sync предназначен для регулярного обновления данных без повторной полной загрузки всех предложений.

Пайплайн использует механизм контрольных точек синхронизации магазинов, чтобы определять, какие магазины требуют обновления.

Это позволяет сократить количество API-запросов и обрабатывать преимущественно изменившиеся данные.

### 3.2. Логика выполнения

Общий порядок выполнения:

1. Создание записи о запуске в `raw.pipeline_runs`.
2. Получение информации об изменениях магазинов через CheapShark API.
3. Сохранение исходного ответа API в RAW.
4. Сравнение полученных временных отметок с контрольными точками в `core.stores`.
5. Определение магазинов, требующих синхронизации.
6. Получение предложений для выбранных магазинов.
7. Сохранение исходных ответов API в RAW.
8. Загрузка и обновление информации об играх.
9. Архивирование предыдущих состояний предложений при обнаружении изменения цен.
10. Обновление актуальных предложений в `core.deals_current`.
11. Обновление контрольных точек синхронизации магазинов.
12. Завершение запуска и обновление его статуса.

### 3.3. Контрольные точки синхронизации

Для определения необходимости обновления используется поле `last_change_unix` таблицы `core.stores`.

Оно хранит временную отметку последнего изменения данных магазина, полученную из источника.

При очередном запуске пайплайн сравнивает значение из API с сохранённой контрольной точкой.

Если магазин требует обновления, его предложения загружаются повторно.

Контрольная точка обновляется после успешного получения и обработки данных магазина.

### 3.4. Пагинация и частичная загрузка

Получение предложений может выполняться несколькими API-запросами с использованием пагинации.

При ограничениях API, например HTTP 429 (Too Many Requests), загрузка может завершиться частично.

В таком случае:

- Исходные ответы уже полученных страниц сохраняются в RAW.
- Полностью загруженные магазины могут быть обработаны.
- Контрольные точки обновляются только для успешно загруженных магазинов.
- Магазины, загрузка которых не завершена, остаются доступными для повторной синхронизации.
- Запуск может получить статус `partial`.

Такой подход позволяет не продвигать контрольную точку магазина, если его данные были получены не полностью.

## 4. История изменения цен

История цен формируется в процессе Incremental Sync.

Перед обновлением актуальных предложений выполняется SQL-трансформация, которая сравнивает существующие записи `core.deals_current` с новыми данными.

Если обнаружено изменение состояния предложения, предыдущее состояние архивируется в `core.deals_price_history`.

В исторической записи сохраняются:

- Идентификаторы игры и магазина.
- Идентификатор предложения.
- Предыдущая цена со скидкой.
- Обычная цена.
- Размер скидки.
- Признак наличия скидки.
- Время последнего изменения по данным источника.
- Время наблюдения предыдущего состояния.
- Время архивирования.
- Идентификатор запуска пайплайна.

После архивирования актуальная запись обновляется новыми значениями.

Таким образом, `core.deals_current` содержит последнее известное состояние предложения, а `core.deals_price_history` — предыдущие состояния.

## 5. Сохранение исходных данных

Все полученные ответы API сохраняются в `raw.raw_api_responses`.

Для каждого ответа фиксируются:

- Источник данных.
- Время загрузки.
- Номер страницы, если применимо.
- Размер страницы, если применимо.
- Количество полученных результатов.
- Исходный JSONB payload.
- Идентификатор запуска пайплайна.

Сохранение исходных ответов позволяет повторно анализировать полученные данные и упрощает поиск причин ошибок при обработке.

## 6. Управление запусками и обработка ошибок

Каждый запуск пайплайна регистрируется в `raw.pipeline_runs`.

Для отслеживания состояния используются следующие статусы:

| Статус | Описание |
|---|---|
| `running` | Пайплайн выполняется |
| `success` | Пайплайн завершился успешно |
| `failed` | Пайплайн завершился с ошибкой |
| `partial` | Пайплайн обработал только часть данных |

При успешном завершении фиксируется время окончания выполнения.

При ошибке сохраняется информация о её причине.

Статус `partial` позволяет отличать частичную загрузку от полностью успешного выполнения и от критического сбоя.

## 7. Принципы надёжности

При проектировании пайплайнов используются следующие подходы:

1. **Сохранение RAW.** Исходные ответы API сохраняются до выполнения трансформаций.
2. **Инкрементальная загрузка.** Повторно обрабатываются только магазины, требующие синхронизации.
3. **Безопасное обновление контрольных точек.** Контрольная точка продвигается только после успешной обработки данных магазина.
4. **История изменений.** Предыдущие состояния цен архивируются до обновления актуальных предложений.
5. **Отслеживание запусков.** Каждый запуск имеет собственную запись в `raw.pipeline_runs`.
6. **Обработка ограничений API.** Частичная загрузка не должна приводить к потере возможности повторной синхронизации незавершённых магазинов.

## 8. Ограничения текущего подхода

Инкрементальная синхронизация основана на получении доступных предложений из API.

Отсутствие предложения в очередном ответе API само по себе не доказывает, что оно окончательно удалено или больше недоступно.

Поэтому отсутствие предложения в ответе не используется как достаточное основание для удаления записи из `core.deals_current`.

Это позволяет избежать ошибочного удаления актуальных предложений при неполной выдаче API.
